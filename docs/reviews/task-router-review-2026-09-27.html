1 · What it is

Its own first sentence — "The deterministic task router for the coding-hermes fleet … A task declares its capability profile (signed levels −5..+5 per category); the registry finds every model that clears ALL requirements; the chain = eligible models sorted by effective price; provider gates (quota / health / circuit) filter at resolve time" — is accurate, and the code backs it: router_spawn.py:149 is literally DEFAULT_SORT = os.environ.get('ROUTER_SPAWN_SORT') or 'price'.

Four moving parts, and it is worth seeing them as separate products sharing one repo:

  • the registry — data/tables/*.jsonl (models, tiers, prices, lifecycle, quality estimates), 881 active lanes over 29 providers, regenerated by router_seed.py from catalog + benchmark + price sources;
  • the resolver — profile + requirements → chain, with machine-readable exclusion codes for every lane it refused, so "why this lane and not that one" has an answer;
  • the gates — provider health, a circuit breaker with class→duration semantics, and static admission control that caps in-flight work;
  • the surface — one OpenAPI 3.1 document, a derived MCP bridge, a web UI, and a proxy that actually performs the hop.

What makes it unlike a general LLM gateway: it does not route on a model string you choose. It routes on a declared capability profile, prices the result in plan-offset normalized dollars, and keeps receipts (usd_1m, price_basis, chain, exclusions) for every decision.

Take: reach for task-router when the hard part is which model deserves a task under a capability floor and a pile of subscription plans whose list prices lie — and when you need to justify the choice afterwards. Reach for LiteLLM or Portkey when the hard part is running other people's traffic safely: virtual keys, budgets, tenancy, and a UI ops teams already know. They are not rivals: task-router's natural home is behind such a gateway as the decision layer, with the gateway owning auth and the outer ledger.

Scoring, per the method's convention: LiteLLM and Portkey score 9/10 inside their scope (traffic management, tenancy, budgets) and 0/10 outside it (they cannot tell you that a signed tool_use: +3 task has seven eligible lanes and why the other 874 were refused). task-router scores the inverse. 4 · How agents hook in

The method's deep-dive lens is written for agent message buses; task-router is not one, so three of the five lenses (push-vs-poll, scale-to-1000, incident-observability of a bus) do not apply and are not faked here.              idempotency keys on the routing API (no HTTP key in the server)

So agents reach it three ways: the OpenAPI document directly, MCP tools derived mechanically from those same paths (a genuinely tidy design — one contract, two transports, no second implementation to drift), or the CLI scripts. The scheduler hook is the sharpest of the three: router_spawn.py must never block a caller, so its contract is fail-open ({"error": ...} and exit 0). That is the right call for a firmware-level dependency and it is documented as "sacred" in the repo's own rules.

5 · What I'd add or change (ranked)

  1. Get CI green on main, and make red-on-main impossible to ignore. Three consecutive failures including the reviewed commit, failing in the full-suite step. Everything else on this list is smaller. The repo already files its own CI rows — the gap is a gate that blocks landing while the suite is red.
  2. Fix the console-script root resolution (cli.py:114). One line: prefer an explicit TASK_ROUTER_HOME/repo-root env or a walk-up to the nearest scripts/router_spawn.py, and fail with a message that says "run from a checkout" rather than a site-packages path. Today the published install path yields a CLI that cannot run one command.
  3. Isolate from the host. A clone I booted read ~/.hermes/model-router/{health,quota,circuit}-state.json and ledger.jsonl from my machine and folded them into its own status output. That is fine for the fleet and hostile to review or CI: a stranger's clone reports someone else's circuit breakers as its own state. Route these through data_home with an explicit opt-in override.
  4. Give it a front door a stranger can find. No Makefile, no Dockerfile, no make test. The eight commands a newcomer needs (venv, install, seed, validate, status, serve, test, guard) are all in the README prose. A 20-line Makefile would make the whole method's step 2 trivial and is the cheapest possible adoption win.
  5. Publish the state schemas. registry.json, the outcome ledger rows, and the circuit/quota state files are the actual interface between this project and everything else in the fleet, but their shapes exist only in code. A schema file per artifact turns three integrations into validation calls.
  6. One-command smoke in CI for the fresh-clone path. The most valuable test in this repo is the one nobody has written: clone → install → seed → status → assert fallback_used: false. That single test would have caught finding #2 and would keep the bootstrap honest forever.

Prior art worth stealing: LiteLLM's virtual-key/budget layer for the outer boundary (so this router never has to grow auth); OpenRouter's error.metadata.limit_source for naming which limit refused a request — the same shape as this repo's exclusion codes, and worth adopting verbatim in the new quota layer; and Prometheus/LiteLLM-style spend metrics keyed by model × key × window, which is what makes budget questions answerable at 3 a.m.

6 · Good things (verified, not asserted)

verified live
  • It confesses its own degradation. Three separate fields (unavailable, warning, note) plus bootstrap: true tell a stranger exactly what state they are in. Rare, and the single best signal in the repo.
  • Deployment truth is machine-checked. /health returns both commit and stale, computed against the tree it was loaded from — a service that cannot lie about which build is running.
  • The refusal vocabulary is first-class. exclusion_codes() turns "why not that lane" into data, not a log line.
  • The circuit breaker learned from its own outage. router_circuit.py maps failure class → duration (overload=120s, quota_window=300s, api_down=1800s, out_of_credit=14400s), separates hard from soft classes, and "fails LOUDLY on an unmapped kind — never a silent api_down default". That is the fix for a real incident written into the code as a rule.
  • Reviewable without spending money. --dry-run on the routing loop, and a read-only server mode that really does refuse writes, mean a stranger can audit this without touching a provider. Most routers cannot be reviewed at $0.
  • Test density is real: 96 test files, 1,166 test functions, plus a separate acceptance battery for the live proxy path.
  • Build is trivial: 2 s clone, 2 s install, stdlib-only, MIT, 76 KB artifact.
  • It manages its own work in-tree — 248 board rows and 450 events — which is why the review could read the project's reasoning instead of guessing at it.

7 · Bad things / rough edges (actually hit)

rough edges
  • CI is red on the commit you would clone. Job test, failed step "Full test suite", on three consecutive runs including 1dc5d6a. A stranger's first impression.
  • The published install path produces a broken CLI. pip install . → router status → No such file or directory: site-packages/scripts/router_status.py. Loud, but total.
  • A clone is not isolated. It silently reads the host's ~/.hermes/model-router/* state; the status output therefore mixes a sample registry with live circuit/quota/health data that belongs to someone else's machine.
  • No build front door. No Makefile, no Dockerfile, no task runner — the eight setup commands live in prose, so a stranger must read 535 README lines before they can run anything.
  • Metadata gaps are the norm, not the exception: the project's own /gaps reports 856 of 881 models missing at least one dimension (benchmark 729, perf 813, sentiment 813, tiers 704, price 42). It states this openly, but it means "the registry finds every model that clears ALL requirements" is frequently satisfied by sparse evidence rather than good evidence — the coverage gate landed for exactly this reason.
  • The reviewed commit is one of 639 in a month (~21/day) with three red CI runs in a row — velocity outrunning the gate.
  • Working tree is 2.8 GB against a 14 MB checkout. By design (state and tables live outside VCS), but it means "clone and run" gives you a sample, and the project's real behaviour is only reproducible on the machine that generated the state.
  • Not criticism, context: the git authors include an AI identity (totalwindupflightsystems) and kara. Worth naming plainly in any report that a third party will read, so it is not mistaken for a human-only project.

8 · Where / how it could actually be used

fits & cautions
  1. As the routing brain for a fleet you own, with subscription plans. This is its actual job today and it does it: plan-offset pricing, capability floors, exclusion receipts. Before trusting it: green CI, and the quota readback wired in (the table landed today; the pacing gate has not).
  2. As a quota accountant and burn-surplus finder. The live readback already shows one account of a subscription pair at $13.02 of $1400 weekly while its twin carries $796.23 — that is the exact question "what subscription quota is about to expire unused, and which project should burn it". Before trusting it: pacing must never route to an exhausted seat; today it can (one provider's seat 1 is already out of credit behind 83 lane rows).
  3. As a teaching artifact for capability-profile routing. The profile → eligibility → exclusion-code → priced-chain pipeline is the clearest worked example of explainable model selection I have read. Before trusting it: a Makefile and a green CI badge, which is what makes a repo approachable.
  4. Do not use it as a multi-tenant gateway for other people's traffic: no tenancy, no per-user budgets, no virtual keys (grepped: zero). Pair it with LiteLLM/Portkey in front, or keep it single-tenant by design.

9 · Verdict

Try it now if you are routing your own fleet's tasks among subscription plans and you need to justify every choice after the fact — the registry, the exclusion codes, the dry-run, and the honesty fields are genuinely good, and nothing else in this space prices a plan offset at all.

Watch it if you are an outsider: red CI on the tip commit, a broken published install path, host-coupled state, and no build front door mean the first hour with this repo is friction that has nothing to do with the idea. All four are days of work, not months — this is a project whose design is ahead of its packaging.

The bar to bet on it: (1) CI green on main with the fresh-clone smoke test in it, (2) the console script works from a clean pip install, (3) state paths honour a data home so a clone is hermetic. Clear those three and the remaining risk is ordinary engineering risk.

Method honesty: this review was done hands-on — fresh clone, its own build, its own commands, its own API — but one intended step (live API negatives + a latency sample) was blocked by my own harness and is reported as missing rather than estimated. The incumbents in §3 were compared statically. Two companion skills named by the method (frontend-design, find-skills) could not be installed in this session — the skills CLI cancelled even with its own suggested non-interactive flags — so this report is designed to the method's structural requirements rather than by that skill, and impeccable (which did install) was run over it instead.
