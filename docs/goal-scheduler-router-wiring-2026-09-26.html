1. The goal

Route every scheduler-dispatched Hermes call through the task router, with a stats/metrics system complete enough that the chain is ordered by measured cost per task by complexity band — and prove it on live fleet traffic without ever taking the fleet down.

Success is not "the router is wired". Success is: a scheduler tick's call is served by a lane the router chose on evidence, the row explains that choice (options, gates, rating, cost, the tick it served), the same number is queryable later, and the ordering demonstrably differs from what raw price would have chosen — with the fleet healthy throughout.

3. Why the fleet is not routed yet

  1. Safety: pointing 332 prompt-mode lanes at the proxy once already saturated the gateway and looped failures (TR-169). Without admission control the proxy converts a caller's bounded retries into an unbounded pile of upstream calls.
  2. Cost: each proxied request pays an extra full-context rating call. Rating must be cached and/or move off the gateway (raw provider endpoint) before fleet volume.
  3. Attribution: without the tick key there is no "per task" — only "per request". The sort cannot be evaluated honestly.
  4. Data depth: the bands the sort would use have median n=1; sorting on that is worse than price.
  5. Reversibility: the flip must be one env value with a proven revert; today it is unreachable either way.

4. Subgoal tree

Each subgoal is stated as an OUTCOME with checkable acceptance. A subgoal is done when the outcome is measured on live traffic — not when code is committed (the failure this list exists to stop).

S1 — The proxy bounds its own work in flight

WhyWithout it, S7 (traffic) re-runs the incident.
DeliverableAdmission: bounded in-flight + bounded queue + explicit retryable refusal; visible in /health; refusals write a ledger row.
AcceptanceN concurrent callers > cap ⇒ never more than the cap in flight, excess gets 429 with Retry-After; a row with route_outcome=rejected; work under the cap unaffected.
StateCode written and wired (gate, refusal, /health). Tests: 4 pass / 5 fail — failing cases are my test harness, not the code; must be green before S7.

S2 — Rating is cheap and stable

WhyThe rating is a model call carrying the caller's whole context; 430 of 495 incident rows paid it for zero work.
Deliverable(a) identical prompts rated once (cache keyed by prompt hash, TTL, bounded, success-only); (b) the classifier calls a RAW provider endpoint instead of the gateway.
AcceptanceSame prompt N times ⇒ 1 rating call (measured); a failed rating is never cached; live evidence the classifier's upstream is not the gateway (its own tokens no longer carry injected context).

S3 — Every row names the TASK it served smallest, highest leverage

WhyThe scheduler sends the tick id in X-Hermes-Session-Key; the router reads it and discards it. Without it, cost-per-task is unanswerable.
DeliverablePersist the caller key on the row; join to tick → project → board task.
AcceptanceA row can be traced to its tick from the ledger alone; a caller sending no key stays null.

S4 — Session truth is settled, and per-request shares are honest

WhyAn inline snapshot of a running session is a floor; session identity is the prompt hash, so meters are cumulative and per-row attribution double-counts.
DeliverableReconciler (timer, off the request path) reading the session API (GET /api/sessions/{id}), settling on idle ≥ N (only 6.8% of sessions ever get ended_at), appending snapshots; deltas between snapshots give per-request shares; backfills existing rows.
AcceptanceSettled totals match state.db; the sum of per-request deltas equals the session total; a snapshot is never served for a session that continued after it.

S5 — Bands earn the right to be sorted on

Why158 of 271 bands sit at n=1 today.
DeliverableA sufficiency floor per band; below it the effective estimate blends toward list price; the row records which basis ordered its chain.
AcceptanceA band with n<floor cannot outrank a priced lane on noisy evidence; the blend is visible in the envelope and the row.

S6 — The ordering is cost-per-task, proven by diff

WhyThe sort exists and is unreachable; TR-049/TR-065 were marked complete with no effect.
DeliverableSwitch the default ordering, guarded by S5.
AcceptanceSame request under old and new ordering ⇒ different heads, both recorded; reverting is one env value and the revert is proven by a resolve; the sort basis is stamped on every row.

S7 — Traffic ramps on evidence, not on enthusiasm

WhyThe last full flip took the fleet down inside ~17 minutes.
DeliverableRoute a NAMED subset of projects first (start small), with the dummy-scheduler harness reproducing their shape at real concurrency, then expand per measured result.
AcceptanceGateway latency and refusal rate stay within bounds at each step; each expansion is justified by that step's numbers; a rollback drill is executed, not just documented.

S8 — The system is observable by a human

WhyThe incident was found by my own probing, not by the surfaces.
Deliverable/health (admission, cache, sort basis) + UI panes; the ledger queryable for tasks, times, chains, refusals.
AcceptanceAn operator can answer "why did this call go to this lane" and "is the proxy refusing work" from the UI alone.

5. Execution sequence and gates

  1. S1 + S2 (safety + rating cost) — the gate for any traffic.
  2. S3 + S4 (attribution + session truth) — the gate for honest per-task numbers.
  3. S5 (sufficiency) — the gate for trusting the ordering.
  4. S7 at a small scale — real traffic begins; bands fill.
  5. S6 once bands clear the floor — switch, prove by diff, keep revert proven.
  6. S8 alongside, not last.
  7. S9 — the re-evaluation below.

6. The last subgoal: re-evaluate, verify, then grow the tree

S9 — Full re-evaluation. Re-run every measurement that justified the tree and compare to the claim made when each subgoal closed:
  • acceptance battery + full suite green on a frozen tree;
  • band depth (how many bands clear the floor) before/after traffic;
  • rating cost per request (tokens + $) before/after the cache and the raw-endpoint classifier;
  • refusal rate and gateway latency under load from the dummy harness;
  • a real resolve diff: old ordering vs new, same request, both heads;
  • per-task attribution: does the sum of deltas equal the settled session total?
Then, as instructed: derive NEW subgoals from whatever the evaluation exposes — including negative results — and file them before reporting done.

7. What I am asking the quorum

  1. What is missing from this tree that would stop the goal being reached?
  2. Which subgoal is in the wrong position (a hidden dependency)?
  3. Is the sequencing honest about the risk that took the fleet down — what would you add before S7?
  4. Where am I still measuring the wrong thing, or marking something done that is only built?
  5. Is there a cheaper path to the same outcome that this list ignores?

8. What I will not do

  • Not switch the ordering on thin data (median n=1) to have something to show.
  • Not route the fleet again without S1 proven under real concurrency.
  • Not mark a subgoal complete on committed code; the outcome must be measured on live traffic.
  • Not report a capability as working because a function exists.

9. Pre-review round 1 (a deliberation, not a quorum) — findings, and the tree it grew

Convened 2026-09-26 on this document (formation: audit — two workers plus a dedicated audit stage). The merged verdict is kept below in substance; every item became a new subgoal or an acceptance rewrite. This section exists because a plan that does not change when reviewed was not reviewed.

Provenance caveat, and it matters: this round ran as a multi-model deliberation, NOT as a seat-based quorum. The canonical skill is explicit that a deliberation call is not a quorum — a quorum is independent judge seats on full sessions, every seat working the same claim checklist, with the coordinator re-verifying every CONTRADICTED lead as the commit layer. Treat the verdicts below as strong leads, not rulings; a seat round is still owed before this tree is frozen.

9.1 The verdicts

  • Q1 — Missing nodes (three, all silently absorbed by existing subgoals). (a) No ingress/cutover proof that scheduler-dispatched calls actually enter the router and that bypass stopped — S3 only persists a key if a call arrives, and S7 ramps a subset, not the dispatch path. (b) No call-density / amplification control: the incident's real mechanism (6.1× session density, 430 of 495 rows with zero upstream work) is unowned, because S1 bounds concurrency in flight and the 44-cap never fired. (c) No band provenance: S5's floor neither retires imported history nor stops median-n=1 bands from contaminating the ordering S6 will switch to.
  • Q2 — Wrong position: S7 is too early. Hidden edge S7 → S3+S4. With 0 of 601 rows carrying the tick id, any traffic before attribution produces permanently unattributed rows that poison the very bands S6 sorts on. Second edge: S6 depends on S4, not only S5 — ranking one task needs per-request session deltas, and session totals alone cannot rank.
  • Q3 — Risk honesty: no. The sequence does not own the fact-5 mechanism. S1 must reproduce the density and zero-upstream signature under the harness; S7 must run at >44 concurrent callers and ≥6.1× density, with the rollback drill executed, before it names its first project.
  • Q4 — Where "built" is being read as "done". Per subgoal: S1 ("the failures are my test harness" is not evidence — run a black-box concurrency rig against the real proxy); S2 (measure upstream provider requests per prompt hash, not cache hits — they diverge under stampede, TTL expiry and retry); S3 (measure the live join rate, not "field added"); S5 (a stamped basis field is cosmetic — show a low-n band cannot become head); S6 (fact 1 stays unfixed unless a fleet process actually sets the variable — capture the env the spawn really sees); S8 (a pane that is empty until S3 answers nothing).
  • Q5 — A cheaper path exists; adopt it. (a) Do not set the ordering variable live as the switch: run it in shadow — stamp the basis and record the cost-sort head while still serving price. (b) A deterministic complexity classifier first, with the model on a ~5% audit sample: fact 3's rating is ~$0.065 input-side only, and at 1M calls that is ≥$65k of model spend to classify. (c) Start traffic on projects that already map to high-n bands (hermes median n=14, max 122,122) rather than on thin ones.

9.3 Acceptance rewrites accepted from the review

  • S1 — replace "tests 4 pass / 5 fail, the failures are my harness" with a black-box concurrency rig: max in-flight ≤ cap under N > cap callers, 429 rows present with a rejected outcome, and under-cap latency unchanged. Built is not done.
  • S2 — measure provider request count per prompt hash and force a provider failure to prove it is never cached; prove the raw endpoint by egress host/URL trace, not by a config flag.
  • S6 — enter through the shadow path: record both heads for the same request, then show the revert returns the price head. "Different heads" alone is not cost-per-task proof, and the switch must never be a bet on thin bands.
  • S8 — an operator answering "why did this call go to this lane" requires S3 to be live first; the pane is empty until then, and that is stated rather than assumed.

9.4 Facts the panel challenged (to re-measure, not to defend)

  • Fact 3 is under-specified: $0.065 is input-side only — the extra ~47k tokens, retries and cache misses are unmeasured. Measure provider-billed cost per rating call over N calls, split input vs output.
  • Fact 2 mixes populations: the hermes median (n=14) hides the router-proxy median (n=1). Report band depth split by source, and for live scheduler-dispatched traffic only.
  • Fact 6's custody boolean is not a measurement: measure per-session state-DB diff and per-request delta sums across all rows, including sessions never ended and sessions continued later.
  • Fact 7's classifier parse state is not a success rate: measure parse failure rate and the selected head against the recorded chain.
  • Fact 10 names no threshold and no holdout: measure the actual regret of below-floor estimates against list price on a live holdout.
  • Fact 1 needs runtime proof: set the variable, spawn, and capture the env the spawner actually sees — an import-time read can hide a stale environment.

9.5 What this changes in the sequence

S3 and S4, green and backfilled, now gate S7 rather than merely precede it. S11 becomes a precondition of any traffic at all, alongside S1. S6 moves behind S12 and enters through the shadow path, so the ordering switch is never a bet. S7's first project set is chosen from bands that already clear the floor. S10 is added because "we are routed" must be a measured number.
