## 1. Semver rationale — why 0.2.0, not 0.1.1

MINOR bump (0.1.0 → 0.2.0). The line since 0.1.0 carries substantial new
capability, not just fixes:

- Complexity scoring on the spawn path — the router now scores the TASK text
  and derives requirements from it (TR-124 design), with fail-open
  degradation to the profile chain. New behavior + new JSON fields.
- Diversity two-knob caps and per-model concurrency skip (TR-007).
- Plan-window quota-exhaustion gates with auto-clearing reset (TR-060).
- Per-provider last-mile upstream routing on the proxy path (TR-118).
- Pricing cache end-to-end + new-model classifications.

A PATCH (0.1.1) would misrepresent a feature release as fix-only. No
breaking CLI contract change was found (the `router` entry point,
subcommands, and documented flags keep 0.1.0 semantics), so MAJOR does not
apply — and the project is pre-1.0 where 0.y is the minor axis.

   change inside a release branch. Justified by criterion 5: tag pushes do
   not trigger the push-branches CI event, so the tag commit is verified by
   dispatching the workflow on it.

4. **Board-row status changes deferred to post-merge** (RELEASE-002 →
   complete, INT-CI-001 → complete, TR-106 → complete-with-evidence): this
   is an isolated worktree; per the isolation doctrine shared-state edits
