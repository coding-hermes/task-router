## 1. What "connect over the muster protocol" means for THIS service

Muster is not re-implemented here — it is consumed. For task-router, "supporting
muster connections" means we are the **spec-publisher and the API**; muster's
binaries are the client engine. Concretely, the surface is four things:

### Surface A — the OpenAPI 3.x contract (already exists, keep it canonical)

- `GET /openapi.json` serves a static OpenAPI **3.1.0** document generated by
  `build_openapi()` in `scripts/router_server.py` [code]. 19 paths, 19
  operations, all with operationIds [measured].
- This single URL is the entire integration artifact a consumer needs. It is
  served live by the same process that serves the API, so spec drift between
  "documented" and "running" is structurally impossible. **This doc makes the
  live URL the canonical spec surface.** Any spec copy (file, repo, docs site)
  is a convenience mirror, never authoritative.
- Contract quality rules that carry forward (all satisfied today [measured]):
  every operation has an operationId; `servers[].url` is absolute
  (`http://127.0.0.1:9092`); no `$ref` indirection; every operation documents
  200/400/500 responses (mutations add 401/403).

### Surface B — the consumer attachment (one config block, zero code)

Because the spec declares an absolute server URL, the minimal consumer block is
exactly (written out verbatim; `--base-url` omitted is **measured sufficient** —
muster resolves the base URL from `servers[].url` per its DF-MUSTER-1 rule):

```json
{
  "mcpServers": {
    "task-router": {
      "command": "/home/kara/muster/bin/openapi-mcp",
      "args": ["--spec", "http://127.0.0.1:9092/openapi.json"]
    }
  }
}
```

Measured behavior of this block [measured]:
- `openapi-mcp` fetches the spec over HTTP from our live server (URL `--spec`
  is supported), handshakes, and generates **19 MCP tools, one per operation**.
- stderr confirms: `Loaded spec: Task Router API (1.0.0)` /
  `Generated 19 MCP tools` / `Using base URL: http://127.0.0.1:9092
  (override=false)`.
- Every OpenAPI operation becomes an MCP tool; every tool becomes a typed JSON
  args → JSON result call (query params like `resolve.project` arrive as
  `required` properties with their descriptions intact [measured on the
  `resolve` tool schema]).
- Offline/file fallback variant (also valid, for air-gapped use):
  `args: ["--spec", "/path/to/openapi.json", "--base-url", "http://127.0.0.1:9092"]`.
  The file copy goes stale silently — the URL form is the recommended default.

### Surface C — the human quickstart (new deliverable for TR-128)

A short doc (suggested home: `docs/muster-quickstart.md`) that gives a human or
an agent operator, in order:
1. the consumer block above (copy-paste),
2. what tools they will see (the 19 names, grouped read vs mutation),
3. the fail-open contract for callers (see §Boundary: "a tool error from the
   router means 'no routing data', never 'stop working'"),
4. the two-line curl pre-checks (`/health`, then the MCP handshake) so a user
   can tell "router down" from "muster misconfigured" before blaming either.

### Surface D — proof-of-life commands (the acceptance battery, §4)

The precise commands and non-vacuous assertions are in §4. They are part of the
scope: TR-127 must freeze them as the acceptance criteria; TR-128 must make
them pass and re-runnable by a verifier with no repo context.

## 2. What is NOT in scope for this row (and its chain)

- **Re-implementing any muster internals.** No parser, no MCP codec, no
  generator, no executor in this repo. Muster owns that pipeline (discover →
  protocol-neutral model → shared CLI+MCP generation → transport); we publish
  a spec and serve HTTP. PROTOCOLS.md makes OpenAPI the first *adapter* — from
  our side, muster is the *consumer*, and we do not need to care about its
  internal seam work (PROTO-001..008) as long as the two binaries keep
  ingesting our spec, which §4 asserts.
- **Consuming other protocols.** gRPC/GraphQL/JSON-RPC/AsyncAPI/SOAP support
  is muster-side roadmap. Nothing in this chain adds a non-OpenAPI surface.
- **Serving muster's daemon / WASM / DSL features from task-router.**
  `openapi-daemon`, `dsl run`, and WASM response plugins are muster features
  this service neither exposes nor depends on.
- **Making mutations a supported MCP consumer story** (see §Boundary and
  §Auth). The seven POST operations remain operator-only over HTTP. They will
  still appear as MCP tools (muster generates a tool per operation; that is
  its contract, and hiding them is muster-side config if it ever exists) —
  the *server* is the gate, and it is proven to hold (§4, probe 5).
- **Remote/public consumer access.** The router binds loopback; keeping it
  loopback-only is the current decision. Any remote or non-loopback consumer
  surface (bind flag, tunnel guidance, auth on reads) is a NEW decision, filed
  separately, because it touches the shared/public-surface doctrine. Named as
  open decision #2 below.
- **Editing `scripts/router_server.py`'s HTTP API shape.** The 19 operations
  and their semantics are frozen by this scope; TR-127/128 change documentation
  and the MCP story, not the API contract. (If a gap forces an API change, it
  is a new row, not scope creep here.)

## 3. Muster-consumability audit of the live `/openapi.json`

**Result: the contract is already muster-consumable with zero blocking gaps.**
Audited field-by-field [measured], muster binary `openapi-cli` built 2026-09-24:

| Check | Status | Evidence |
|---|---|---|
| Spec version | PASS | `openapi: 3.1.0` — muster's kin-openapi v0.148.0 parser ingests this exact document, not just "3.x documents" in the abstract [measured: `openapi-cli discover http://127.0.0.1:9092/openapi.json` exit 0, all 19 operations listed with IDs]. The board row's 3.0-vs-3.1 worry is settled by measurement: 3.1 parses. |
| operationIds | PASS — no gaps | All 19 operations carry operationIds (`getOpenAPI`, `getHealth`, `resolve`, `recordCircuit`, …). IDs are unique and survive muster's name normalization [measured: they appear verbatim as MCP tool names]. |
| `servers[].url` | PASS | Absolute `http://127.0.0.1:9092` [measured: muster's stderr resolves it with `override=false`; no `--base-url` needed]. |
| Auth schemes | PASS with one documented behavior | One scheme: `EditApiKey`, `type: apiKey, in: header, name: X-API-Key`, declared op-level on the 7 POSTs; no global security [measured]. Muster supports apikey-header auth, but does NOT auto-map the spec's securitySchemes into its executor [measured: no securityScheme handling in muster's `pkg/mcp`/`pkg/client`; auth is explicit muster-side config: `auth: {type: apikey, apikey: {header: X-API-Key, value: ${API_KEY}}}`]. This is a muster behavior to document, not a defect in our spec. For the recommended read-only consumer surface it is irrelevant (§Auth). |
| Response shapes | PASS | All 19 ops document 200/400/500; the 7 mutations add 401/403 [measured]. Bodies are plain JSON objects (consistent `{"error": string}` error shape); no streaming, no file downloads, no callbacks/webhooks → every operation is unary, so PROTOCOLS.md §4.5 (unbounded/streaming/bidi MCP safety) is trivially satisfied: muster needs no transcript envelopes for this API. |
| `$ref` usage | PASS (vacuous) | Zero `$ref` in the document [measured]. Nothing for the parser to misresolve. |
| Schema fidelity | PASS | Query params arrive in MCP tool inputSchemas with types and descriptions intact [measured: `resolve` exposes `project` (required, string), `sort`, `window_h`, etc. with their descriptions]. |
| MCP-level round trip | PASS | `tools/list` → 19 tools [measured]; `tools/call getHealth` returned the live health payload (status ok, 1563 models, 26 providers) through muster's server [measured]. |

Non-blocking observations (recorded so TR-127 can decide, not discover):

1. `resolve.sort`'s value vocabulary (`price | predicted_cost_per_task |
   wall_time | ratio:<w>*<cost>+<w>*<time>`) is described in the field's
   description text, not as a schema `enum`. Harmless for muster (it passes
   the string through; a wrong value 400s cleanly). Optional tightening: make
   it an enum in a future API row. NOT required for muster.
2. The MCP protocol version strings differ between the two live bridges
   [measured]: muster's `openapi-mcp` answers `initialize` with
   `protocolVersion: "2024-11-05"`; the repo's hand-rolled `POST /mcp` bridge
   answers `"2025-03-26"`. Both completed handshakes and served 19 tools to a
   client requesting `"2025-06-18"`. Not a blocker (measured working), but it
   is a parity datum for the consolidation decision (§Bridge).
3. Muster renders HTTP errors to the agent as text
   `"Error: HTTP 403: {\"error\": \"read-only mode\"}"` with `isError: true`
   [measured]. Callers must parse text content, not structured errors. Fine
   for the fail-open contract; worth one line in the quickstart (Surface C).

## 4. Proof plan (the acceptance battery for TR-127/TR-128)

Run against a LIVE router instance. Preconditions: router running (default
**read-only** mode — verify via `GET /health` → `"mode":"read-only"` before
starting; probe 5 below MUST run against read-only, never edit mode), muster
binaries at `/home/kara/muster/bin/`.

All commands verified verbatim on 2026-09-24 [measured]. Assertions are
non-vacuous: each names data only obtainable from a true end-to-end pass.

**Probe 1 — muster ingests the live spec.**

    /home/kara/muster/bin/openapi-cli discover http://127.0.0.1:9092/openapi.json

Assert: exit 0; output contains exactly the 19 operationIds (12 reads +
7 mutations). `jq -r '.paths | to_entries[] ...'` against
`curl -s http://127.0.0.1:9092/openapi.json` is the ground-truth list.

**Probe 2 — the consumer block generates the full tool set.** Pipe over
`openapi-mcp`'s stdio, in order: `initialize` (protocolVersion
`2025-06-18`), `notifications/initialized`, `tools/list`. Assert: initialize
result has `serverInfo.name == "openapi-mcp"`; `tools/list` returns exactly
19 tools; the tool-name set equals the operationId set from probe 1
(set equality, not count equality — count equality hides renames); every
tool has a non-empty `inputSchema`.

**Probe 3 — a read executes against the live service through MCP.**
`tools/call` with `{"name": "getHealth", "arguments": {}}`. Assert: response
`isError` absent/false; `content[0].text` parses as JSON;
`.status == "ok"`, `.registry.models > 0`, `.registry.age_days == 0` (live,
fresh registry data — a mocked or dead upstream cannot produce this).

**Probe 4 — the crown-jew read works.** Obtain a valid project id from the
`listProfiles` tool result (or `GET /profiles`), then `tools/call`
`{"name": "resolve", "arguments": {"project": "<id>"}}`. Assert: well-formed
chain result or a well-formed error — either way JSON-parseable. The
fail-open contract point: an error result is an ACCEPTABLE outcome (the API
may have no data); a hang, a crash, or an unparseable tool result is a FAIL
(the router must never trap an agent loop; cf. PROTOCOLS.md §4.5 rule 1).

**Probe 5 — the mutation boundary holds through MCP (negative proof).**
`tools/call` `{"name": "recordCircuit", "arguments": {"provider":
"probe-provider", "model": "probe-model", "outcome": "failure", "reason":
"muster acceptance probe"}}`. Assert: `isError == true`; text contains
`HTTP 403` and `read-only mode`; **and** `GET /circuit/status` (or the
`getCircuitStatus` tool) returns identical open-pair/class counts before and
after the call — proving state was not merely refused but untouched.
Measured 2026-09-24: exactly this outcome [measured]. Probe 5 defines the
safety property: **the server, not the client, is the gate.**

**Probe 6 — bridge parity / drift guard (while two bridges exist).**
`POST /mcp` `tools/list` on the same server. Assert: the same 19 tool names
as probe 2. This is the standing drift alarm between muster's generation and
the hand-rolled bridge until the bridge retires (§Bridge). After retirement
(TR-128), this probe inverts: assert `POST /mcp` returns 404.

**Probe 7 — canonical spec freshness.** `openapi-mcp --spec
http://127.0.0.1:9092/openapi.json` (URL form) stderr shows
`Using base URL: http://127.0.0.1:9092 (override=false)`. Assert the URL
form, not a file copy, is what the quickstart ships — a file copy rots
silently; the URL form cannot.

A verifier that runs probes 1–7 and meets every assertion has proven: spec
published, muster ingests it, MCP tools generate, reads execute live,
mutations are gated, the two surfaces agree, and consumers always see the
current spec. That is the full meaning of "connectable over the muster
protocol" for this service.

## 5. Boundary call: which operations are agent-safe over MCP

All 19 operations are **unary** request/response (no streaming) — muster's
agent-safety machinery (PROTOCOLS.md §4.5) is trivially satisfied. The safety
boundary is therefore about *semantics*, and it falls exactly on the
read/mutation line already in the spec:

**Agent-safe (12 reads — the recommended MCP consumer surface):**
`getOpenAPI`, `getRoot`, `getHealth`, `getStatus`, `getModelStatus`,
`listProfiles`, `listProviders`, `getCircuitStatus`, `getGaps`, `getPricing`,
`getChains`, `resolve`. These are exactly the operations an agent needs to
route work: status, chains, price checks, and chain resolution. All are
idempotent GETs with no side effects [code: dispatch table].

**Gated (7 mutations — never a default consumer surface):**
`recordCircuit`, `startLedger`, `endLedger`, `ingestOutcome`,
`updateProviderListing`, `updateModelListing`, `updateProfileListing`.
Defense is layered, and the layers live OUTSIDE the MCP layer on purpose:

1. **Server mode gate (the real one, proven):** a read-only-mode router
   rejects every mutation with `403 {"error": "read-only mode"}` before any
   handler runs [code: `RouterApplication._authorize` returns before
   dispatch; measured end-to-end through muster's MCP server in probe 5].
   Production runs read-only by default; edit mode additionally requires
   `ROUTER_EDIT_API_KEY` to be set or the process refuses to start [code].
2. **Key distribution:** in edit mode, mutations require `X-API-Key`
   (constant-time compared [code]). Muster consumers only send it if an
   operator explicitly configures muster-side auth (§3, auth row) — a
   generated client cannot acquire the key by accident.
3. **Fail-open compatibility (the board row's question):** the router's
   fail-open rule ("router errors must never block the caller") is a CLIENT
   policy, and muster's generated clients preserve it structurally: every
   failure arrives as a bounded, well-formed tool result (`isError: true`),
   never a hang. The API is also fail-open at the data layer (degraded lanes
   and missing stats still yield a chain). The quickstart states the caller
   rule: a router tool error means "no routing data — proceed on your own
   judgment", never "stop".

Ruling embedded in this scope: the mutation tools being *visible* over MCP is
acceptable; the mutation tools being *executable* by an unattended agent is
not. The server-side 403 is the enforcement, and probe 5 is its regression
test. No muster-side tool filtering is required for this scope (and none was
verified to exist — do not assume muster offers one).

## 6. Auth story: this service's credentials vs what muster can carry

| Layer | Mechanism | Measured/code status |
|---|---|---|
| Reads (12 ops) | **None.** Loopback binding (`servers[].url` = `http://127.0.0.1:9092`) is the entire access control. | The running instance binds 127.0.0.1 [measured via /health + spec]. |
| Mutations (7 ops) | `X-API-Key` header (scheme `EditApiKey` in the spec), honored only when the process was launched `--mode edit` with `ROUTER_EDIT_API_KEY` set. | [code: argparse + env check + `hmac.compare_digest`; measured 403/401 behavior]. |
| Muster side | Auth is configured in muster (config file `auth: {type: apikey, apikey: {header: X-API-Key, value: ${API_KEY}}}` or env `MUSTER_AUTH_APIKEY_VALUE`); muster does NOT read the spec's securitySchemes. | [measured: no securityScheme mapping in muster's pkg/mcp / pkg/client; config guide documents explicit auth config]. |

Consequences for this scope:
- **Read-only MCP consumers need no credentials at all** — the consumer block
  in §1 Surface B is complete as written. This is the recommended and only
  supported consumer posture.
- **A mutation-capable muster consumer** would require THREE deliberate human
  actions: operator launches the router in edit mode with a key, distributes
  the key, and configures muster-side auth to send it. Two of those are
  operator-only steps that never appear in any quickstart. This scope does
  not support that posture; if a real consumer needs it, that is a new
  decision (open decision #3).
- **Remote consumers** (different host): out of scope (§2). Loopback-only
  stands until the operator rules otherwise.

## 7. Bridge consolidation: muster vs the hand-rolled `POST /mcp` (TR-018)

Measured state [measured 2026-09-24]: the repo already runs TWO bridges over
the same API. The hand-rolled bridge (TR-018, `POST /mcp` inside
`router_server.py`) answers `initialize` (protocolVersion `2025-03-26`) and
serves 19 tools; muster's `openapi-mcp` answers (protocolVersion
`2024-11-05`) and serves the same 19 tools. Two generators + two executors
over one API is precisely the drift risk this row exists to prevent — probe 6
is the alarm until consolidation lands.

**Scope decision: muster's `openapi-mcp` is the canonical MCP surface for
agent consumers.** The hand-rolled `POST /mcp` is retained through TR-127 as
a zero-dependency compatibility surface (it needs no muster install, which
has value for the bare-host scheduler), and TR-128 retires it after parity is
proven: delete the `/mcp` route + tool derivation, keep `build_openapi()`
(which serves BOTH bridges and outlives them). Probe 6 flips to assert the
404.

Recommendation recorded for TR-127 (not yet frozen — open decision #1): the
TR-018 bridge's only measured advantages are "no external binary" and the
newer protocolVersion string; muster's advantages are a maintained MCP
implementation, audit logging (`-audit`), WASM response transforms, log
control, and the fact that its tool generation and execution are the thing
muster actually tests. One maintained bridge, one drift alarm in CI.
