1. The flip

The scheduler calls Hermes at gateway.url, default http://127.0.0.1:8642. Today that value is unset, so ticks talk to Hermes directly and the router is only in the loop for model selection (router_spawn.py), not for the calls themselves.

Pointing it at the proxy puts the router in the middle of every Hermes call:

SCHEDULER_GATEWAY_URL=http://127.0.0.1:9391     # the proxy; revert by unsetting

# same path, same key, same body — the proxy mirrors /v1/responses and
# returns the gateway's own headers and session id unchanged.
Two operational notes before you flip.
  • A proxy restart drops in-flight proxied traffic. Measured today: a long run died at 84.7 s because a deploy restarted the proxy mid-request. Deploy the proxy outside tick windows, or accept that a restart costs the calls in flight.
  • Fail-open is deliberate. The proxy never blocks a caller: any internal error returns an envelope with the reason and the tiers it tried, so a router fault degrades selection, not the tick.

4. The blocker: why the scheduler's shape is unrated

Same box, same minute, two prompts, two different paths — this is the whole problem in two rows:

Live callcomplexity_sourceProfile chosenTokens in / outCost
chat path — “haiku about a broken pipe”classifier{creative: 0}46,325 / 202$0.0657
/v1/responses — the scheduler's shapedefaultP0_FORE (priciest)46,596 / 3$0.0652

The stated reason is on the row itself:

"problems": ["no JSON object in classifier output"]

The classifier ran (model: deepseek-flash, prompt_version: v1); it answered in prose instead of JSON, the extractor found no object, the rating was abandoned, and the request fell back to the most expensive profile available. The answer itself was three tokens. The bill was 46,596 input tokens at a frontier price — because the gateway injects a large context into every call, profile choice multiplies over a big number.

Two parts to the fix, and they are independent:
  1. Make the parse survive prose. Strip code fences, take the outermost balanced object, and retry once with a JSON-only instruction before giving up. The failure mode is a formatting slip, not an inability to rate.
  2. Make the fallback cheap instead of precious. This is the decision below (TR-139). A bad cheap choice is recoverable; a silent jump to the priciest lane bills frontier prices for a haiku.

Honest limits of this number. 65 proxied rows exist; 53 predate the stats row and carry no verdict, 10 are my own probes that declared a profile (which bypasses the classifier entirely), 1 was rated, 1 was this parse miss. The mechanism is proven; the failure rate is not yet measurable, and I will not quote one. That is also why the fix ships with a counter (rated vs fell-back, by path), so the rate becomes visible instead of inferred.

5. Does task-router have a web UI?

CORRECTION, 2026-09-26. An earlier version of this report said no UI existed. That was wrong: scripts/router_web.py (686 lines, TR-017) is a web UI and has been in the repo since 31 August. It was simply never deployed — no service unit, nothing listening on 9093 — so from the live surface it looked absent. This section now describes what is actually there.

What exists: a stdlib-only, single-page dark UI with inline HTML (no CDN, no build step) and two panes:

PaneDoes
Previewpick a profile or project, resolve via the real router_spawn.py subprocess, render the chain — it never re-implements resolve
Settingsproviders / profiles / discounts tables, edited through the same edit-gated path as the API server (ROUTER_EDIT_API_KEY, X-API-Key); read-only with no key configured

Its JSON surface serves live data today: /api/profiles (1,054 bytes) and /api/settings/providers (8,648 bytes) both answer 200.

Deployed during this report: task-router-web.service (systemd user unit, enabled, Restart=always, loopback-only, read-only mode). It answers HTTP 200 with a 12,319-byte page at http://127.0.0.1:9093/. --mode edit requires a deliberate operator action; a restart can never turn writes on as a side effect.

What it is not (yet): a data command center. There is no ledger search, no row browser, no charts, no traffic view, no per-request flow drill-down and no board browser. That is exactly what TR-150 plus its parts TR-151…TR-156 build — extending this page, not standing up a second UI, so there stays one place to look.

6. Decisions that are yours

  1. TR-139 — what should happen when the rating step fails?
    Recommended: fall back to the cheapest eligible profile and raise an alert. A cheap mispick is recoverable and visible; today's behaviour silently bills frontier prices on a formatting slip. The alternative — keep P0_FORE and alert — protects quality on genuinely complex work but spends max on every classifier hiccup.
  2. TR-146 — where should the proxy read the gateway credential for its capabilities probe? The probe has never authenticated (401 at every boot), so capability discovery has been empty since day one. Options: read it from the service environment at start, or read it from a runtime file. This is a placement decision about a secret, so it is yours, not mine.
  3. Scheduler spawn credential. POST /projects/{ns}/spawn needs an operator credential (SCHED-GAP-1602) and returns 401. Without it I cannot trigger the foreman deliberately and must wait for ticks. Tell me where the credential lives (name only) and I will wire it read-only.
  4. Rotation. Five key names were travelling through ps-visible argv across 8 fleet scripts — fixed today, but rotating them is your call: DAGGER_API_TOKEN, the scheduler KEY, the sub-scout-dry provider keys, API_KEY (Tailscale), OPENROUTER_API_KEY.
