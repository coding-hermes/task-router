TR-414 — bound the spawn-path outcome-ledger scan to the quota window
=====================================================================
Date: 2026-11-25
Host: karaHermes-mde-7840hs (16 c), load average 22.0 -> 39.8 during the run.
Repo: task-router. Base: origin/main 84953703.

DEFECT (as filed)
-----------------
scripts/router_spawn._quota_order_ctx() built the TR-213 headroom term by
calling router_outcomes.load_outcome_rows(outcomes_path()) — a whole-store
tolerant JSONL scan — then grouped the rows per provider for _lane_headroom.
A per-provider WINDOW aggregate cost O(store) on every resolve.

FIX (read path only; no ordering, pricing or accounting change)
---------------------------------------------------------------
1. router_quota_accounting.widest_window_cutoff(limits, now, margin=3600)
   The EARLIEST window start over every provider entry in the limits config
   (each provider owns its own kind: rolling_5h / rolling_daily / daily /
   rolling+Nh / weekly / monthly; `default_window` covers entries that declare
   none), minus a 1 h margin. A row older than that is outside EVERY window at
   once, so it cannot move any headroom. None (never a guess) when no bound is
   derivable -> the caller keeps the whole-store scan.
2. router_outcomes.load_outcome_rows_since(path, cutoff, settle_rows=512,
   chunk_bytes=1 MiB, max_bytes=256 MiB) + iter_tail_lines()
   Walks the store BACKWARDS from EOF in bounded chunks and stops after 512
   consecutive rows older than the cutoff. Torn lines are skipped loudly
   (same doctrine as load_outcome_rows, TR-244); rows are returned
   oldest-first. (None, stats) on cap/unreadable/missing store -> the caller
   falls back to the whole-store scan.
3. router_outcomes.parse_row_ts() is now THE authority for a ledger timestamp;
   router_quota_accounting.parse_ts() delegates to it, so the window scan and
   the accounting view cannot disagree about which rows a window owns.
4. router_spawn._quota_order_ctx() uses (1)+(2), records how the ledger was
   read on the internal ctx['scan'] (never serialised into the resolve doc),
   and falls back to the whole-store read on any error WITHOUT disabling the
   quota term.

WHY A SETTLE RUN, NOT "STOP AT THE FIRST OLD ROW"
-------------------------------------------------
The live store is NOT ts-monotonic: 111,027 of 496,884 rows (22.3%) are older
than the row before them (concurrent sessions complete out of order). A
first-old-row stop would truncate real in-window rows, so the stop rule is a
consecutive run. Measured on the live store (origin/main, 2026-11-25), in-window
rows MISSED by the rule, by window and settle size:

    window   in_window   K=64   K=256  K=1024  K=4096      (missed rows)
    5h           224       0      0       0       0
    24h        1,748       0      0       0       0
    7d        12,802       0      0       0       0
    31d       82,728       0      0       0       0

Rows parsed (live store, one _quota_order_ctx() call, in-process counter):
    5h window  :    303 rows     24h: 1,812    7d: 12,903    31d: 82,886
The shipped settle is 512 — 8x the smallest K that showed zero misses above.

RESIDUAL (named, not hidden)
----------------------------
The live limits config declares ONE provider with a MONTHLY window, so the
cutoff is ~25 days and the bounded read is 62,711 rows / 226 MB of the 541 MB
store — an 87% cut in parses and 58% in bytes, not the 300-row read a 5h-only
config would give. Two further levers, deliberately NOT taken in this card
(each changes more than the read bound):
  (a) provider-scoped prefilter: skip json.loads for lines that cannot contain
      a provider that owns a limit (byte substring test is sound — equality
      implies containment). Would cut the live month scan to a few hundred
      parses with the same byte read.
  (b) rows for a provider with no limit entry are provably irrelevant to
      _lane_headroom (cfg {} -> headroom None); they are still passed through
      today, keeping ctx['rows_by_provider'] an honest window view.
