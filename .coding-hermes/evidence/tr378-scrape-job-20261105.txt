===========================================================================
The units execute /home/kara/task-router directly and that checkout is 4 commits
behind origin/main, so a restart alone would reload the pre-/metrics code. The
documented deploy sequence (docs/graceful-restart.md, scripts/router_deploy.py):

  cd /home/kara/task-router
  git status --porcelain -- scripts     # must be empty (empty at gate time)
  git pull --ff-only                    # 8a735f5 -> b667506
  python3 scripts/router_deploy.py      # dry run, then:
  python3 scripts/router_deploy.py --apply
  # expect: curl -s 127.0.0.1:9391/health | jq -r .code.loaded_source_sha == ab821c81454dd93f

NO PROMETHEUS ACTION IS NEEDED AFTER THE RESTART: the job is already loaded and
will flip to up on the next 30s scrape. Verify with:
  curl -s http://fleet-monitor:9090/api/v1/targets | jq -c '[.data.activeTargets[]
    | select(.labels.product=="task-router") | .health]'      # expect ["up","up"]
  curl -s --data-urlencode 'query=count(up{product="task-router"}==1)' http://fleet-monitor:9090/api/v1/query

Why the fast-forward was NOT done by this tick: the units' modules are imported
at boot but router_server shells out to scripts on every request (_proxy_chain ->
router_spawn.py), so swapping the tree under the running processes produces a
mixed-version LIVE serving state for an unbounded window. The documented sequence
is ff + apply together; the apply half is owner-gated, so the ff is deferred with
it rather than creating that window.
