Completeness: what the mechanical actually is

Bane asked what part of the pipeline to add for better project completeness, then said the direction was right but “missing the mechanical” and called the quorum. Four seats, four model families, one brief, 3 minutes 31 seconds of wall time. Every claim a seat made was re-verified against raw data before it was ruled.

The verdict on my own proposal

My central mechanism is refuted by our own board. I proposed that a row cannot complete without acceptance criteria. TR-011 — the row that claimed “router cleared to move traffic” and was never true — carries four acceptance criteria and guard=PASS. My gate would have passed it. All four seats flagged this independently; qwen verified it from the board. The gate has to be an outcome probe replayed at the commit boundary, not a requirement that criteria exist.

2 · The six mechanisms put on trial

Each stated as a mechanism the seats could attack, not a philosophy they could nod at.

M1  acceptance criteria become {predicate, command, expected}; boardctl refuses a
    transition to complete while any criterion lacks a check
M2  evidence becomes a run record {command, exit_code, stdout_digest, commit_sha, ts}
    instead of a sentence
M3  one writer (boardctl complete) plus detection in CI for writes that bypass it
M4  a gitreins verdict bound to the merged commit - kills --skip-tier2 silent
    completion AND the verdict that judged a pre-merge tree
M5  project attribution + derived completeness; the tick report is GENERATED from
    the projection rather than narrated
M6  standing numbers: unproven-complete, routed share, complexity coverage

4 · The refutation: TR-011

TR-011  status=complete   acceptance_criteria=4   guard_result=PASS
        commit=4257241    evidence_run_id=None   ci=None
        claim: "Full CI pass + live E2E readiness - router cleared to move traffic"

        criterion 1: GitHub Actions CI green on main (tests + guard parity + smoke + integrity)
        criterion 2: live scheduler spawns resolve via the router (ROUTER lines + SPAWN head)
        criterion 3: all registry projects resolve with 0 errors / 0 empty chains

Every one of those criteria is a component claim. CI was green. The guard passed. The spawns did resolve. And the traffic flip never happened — the row was withdrawn months of component-green later. A criterion set can be fully satisfied and still describe a component while the outcome everyone is waiting for stays dark. That is the exact gap the mechanical has to close, and my M1 did not close it.

5 · Two corrections against the coordinator

The doctrine says the highest-value output of a round is a seat contradicting the coordinator. Two landed, and one of them is a number I had already given Bane.

A. My boardctl inventory was stale — the interface is already built

My brief told the seats that boardctl offers list / show / create / update / event / header / validate / stats and that M2 would have to be built. Wrong. Live surface, read from the binary:

init  list  show  create  update  event  header  validate
sweep-status  doctor  version  stats  render  import ...

create --evidence-run-id RUN       update --evidence-run-id RUN
update --status complete --commit-hash SHA --guard PASS|FAIL|SKIP --ci GREEN|RED|SKIP
sweep-status: normalizes known read-aliases; NEVER guesses an unknown status

So M2 is not a build, it is a switch-on — and measured, 0 of 299 rows use it. sol caught this; my brief had the wrong truth in it.

B. My “0 of 1,500 rows carry chain evidence” was a sampling artifact

I quoted the tail of the ledger and concluded the routing evidence was missing from real traffic. Over the last 40 MB — 78,479 rows (52× my sample) the picture inverts:

source_systemrowswith chain evidenceshare
router-proxy1,03283080%
hermes39,43900%
pi37,87400%
opencode13400%

The router writes the evidence — 80% of its own rows carry it. The other paths never emit it because they never go through the router. My conclusion survives; my figure was wrong by an order of magnitude: the proxy-sourced share is 1.3%, not 0.13%. I have corrected it on the record and in the row.

6 · The mechanical, ranked

1

Switch on the interface that already exists

boardctl update --status complete already accepts --evidence-run-id. Measured: 0 of 299 rows use it. Make it required, and add the rule to boardctl doctor so "complete rows with no evidence run" becomes a queryable number instead of a review opinion.

source: sol + post-round measurement
2

Replay, not read

A stored stdout_digest read back as proof is a success marker - the text-as-state sin we already suffer. CI must RE-EXECUTE the recorded command for every row whose status changed in the diff. A digest that cannot be reproduced does not count.

source: sol (C4)
3

Outcome-probe library, authored before dispatch

The criterion that would have caught TR-011 is an outcome probe: "a request through the live ingress resolves with at least one hop", "routed_share moved", "complexity populated on new rows". Probes are chosen from a library BEFORE dispatch by the coordinator, never by the agent that will claim completion. Authorship is the whole point - TR-011 had four criteria and a PASS guard and still lied.

source: kimi (C3) - the fix for the unanimous authorship failure
4

Commit-boundary gate

The gate belongs at the merge/push boundary, not only inside boardctl: append-only JSONL is doctrine, so hand-appends, cron, foremen and git merges are all real writers (today the actual writer is ~/.hermes/scripts/board_append.py). Extend the existing pre-push/CI gate to refuse a diff that flips a row to complete without replayable evidence bound to a commit ancestor-or-equal of origin/main.

source: C2, 4 of 4 seats
5

The one number: verified_complete_share

Two families converged on the same metric independently: complete rows whose evidence REPLAYS green at a commit ancestor-or-equal of origin/main, over all complete rows. It replaces unproven_complete_rows, which is fakeable downward - complete fewer rows and it improves.

source: qwen + sol (C6) + kimi (the gaming vector)
Outstanding precondition — not glossed

boardctl accepts --evidence-run-id but no store for evidence runs was found. The only code references to the field are two unrelated audit scripts. Where runs live (a runs table, the gitreins verdict store, the ledger) is a decision that must be made before anything is built on top of replay.

7 · boardctl’s real surface (the stale-inventory lesson)

Worth its own section because it is a repeat-offence in miniature: doctrine, docs and briefs describe the tool we had, not the tool we have. sweep-status already refuses to guess an unknown status — the same instinct this round is asking for — and nobody was using it, which is why the board still carries a non-enum done and a NULL status. Before building a gate, read the binary.

9 · Method, and what this round is not

  • Transport: four fire-and-forget HTTP seats against the gateway, identical brief, separate processes, no shared state. All four returned the mandated detector line. Wall time 3m31s against a 50-minute budget.
  • Seats were verified live before seating — each lane answered a probe request. Registry entries for two of them are currently marked disabled while the gateway still serves them; that discrepancy is noted, not hidden.
  • Not taken as evidence: one seat frames several findings as “VERIFIED, I ran it myself on this box.” The gateway seats hold no filesystem. Every checkable claim was re-derived by the coordinator against the board, the binary and the ledger instead.
  • What this round is not: it is not a tested fix. It is a ruling on a design, with the authorship flaw proven from our own rows. The mechanisms still need building, testing and a green CI to land.
