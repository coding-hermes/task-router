Dynamic complexity: prompt → scorer → chain

Where the design stands today, measured. The short version: your design is already mostly built — one precedence field defeats it, and three defects keep it from being trustworthy.

✔ scorer selectable (LLM or JEV) — live ✔ prompt-classified by default — 56 of 84 proxied rows ⚠ a declared profile still beats the prompt ✘ classifier cost never attributed

1 · The design we agree on

caller sends a prompt
        │
        ▼
  scorer chosen by settings   x-router-scorer header  or  ROUTER_SCORER env
        ├─ llm classifier   (deepseek-flash, prompt_version v1)
        └─ jev              (cheap alternative scorer, 0-2 bands)
        │
        ▼
  capability matrix   levels per category, filled from the prompt
        │
        ▼
  chain   eligible lanes → gates (quota / health / circuit) → price order → serve
        │
        ▼
  outcome row  →  rolling averages keyed by complexity band  →  next chain is better

Nothing declared up front, no per-project preset deciding what a task is. The profile is a reading of the prompt, and it moves when the prompts move.

3 · The one place the fixed list still wins

this is the whole design shift
server:  return 'declared', {'profile_id': declared, 'matrix': None, ...}
spawn :  21 references to profile_id;  server: 12

/profiles -> P0_FORE   "Default foreman: board ops, audit, dispatch, gap-free reports"   v1, created 2026-08-27
             P1_CODING "Fleet coding: feature work, refactors, tests, bug fixes"

A caller that declares a profile gets source: 'declared' with matrix: None — the prompt is never read. That is why lanes behave like preset buckets no matter what the task actually says. Changing this precedence is the shift you are describing.

The one list I'd argue must survive is policy: allow/deny and reach constraints ("this project's code never goes to provider X"). That is not a complexity judgment and cannot be inferred from a prompt. Keep it, and keep it clearly separate from complexity.

4 · Three defects, all measured

a. The scorer answers in prose on real prompts

row router-proxy-1790640456226-0072-168718ed   (a real Hermes prompt, 7,652 chars)
  complexity_source : default
  degrade_reason    : no JSON object in classifier output
  classifier        : {source: default, parse: no-json, model: deepseek-flash,
                       prompt_version: v1, problems: ["no JSON object in classifier output"]}
  profile_id        : P0_FORE        <- the floor, not a reading of the task

On a prompt that size, "nothing is pressurised" is simply wrong. The parse fail-opens to the floor profile, and the row then looks like a decision when it is an absence.

b. The second scorer has three samples

data/classifier/jev-bands.jsonl   3 rows
data/tables/category_levels.jsonl 264 rows   (the level vocabulary, not a task list)

JEV is wired end to end but almost never exercised — a second opinion that has been asked twice is not yet a second opinion.

c. Nobody pays for the classification

The scorer is an LLM call on every prompt, and its cost and latency are recorded nowhere in the row. Any "cost per task by complexity band" number built on these rows is missing its own overhead.

5 · Two questions that change the contract

1. Who wins: the declared profile or the prompt?
My recommendation: the prompt wins for every pressurised category; a declared profile survives only as policy (floor, ceiling, allow/deny). If you want the declaration gone entirely, the scheduler has to stop sending it — that is a scheduler change, not a router one.
2. What is the scorer default?
Either keep classifier with x-router-scorer as a per-call override, or default to auto so a no-json falls through to JEV instead of costing us the classification.
