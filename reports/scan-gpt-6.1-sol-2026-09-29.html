3 · The gap, stated plainly

why an import is not just "add the id"
  • Nothing to route to. models.jsonl contains 0 rows matching 6.1. The newest sol family we have is gpt-5.6-sol, gpt-6-sol and gpt-sol-latest — all on clinepass.
  • And that family is unpriced. public_price is NULL on every one of those rows; 477 of clinepass's 498 rows are unpriced. Import the id without fixing the price source and the lane lands as NULL — ranked last or unpriced-by-design, which is not the same as "available".
  • A catalog aggregator is not evidence about our lane. models.dev's opencode lists the model; our opencode-go-2 catalog does not. One live call settled a question two catalogs disagreed on.
  • Side finding from the same scan: deepseek-foreman answered HTTP 401 — a foreman lane with a dead key.

Filed as TR-246 with six criteria, including provenance-or-explicit-NULL on the price and tier data or a named missing dimension (the TR-221 standard).

4 · How the scan ran (and its limits)

our side : each config provider -> base_url + key from the environment (by name, never printed)
           GET {base}/models, then match /6\.1[-_.]?sol/i
models.dev: GET https://models.dev/api.json -> 225 providers, matched the id across all of them
result   : 34 endpoints queried -> 19 answered with a catalog, 11 were not providers at all
           (my config parse also caught non-provider keys: canon/vision/tts/curator... - reported, not hidden),
           2 unreachable (bitwarden, the local :9395 router), 1 HTTP 401 (deepseek-foreman),
           1 with no key resolvable by name (minimax)

What this scan does not prove: that the lanes serve the model (a catalog listing is not a completed request), what each lane actually bills for it, or that the id is stable — the model is hours old. The next step is one real request per lane, which is what the import row's third criterion asks for.

A unit trap worth stating: the on-disk state reports 51 DOWN model entries of 183, while this run reports 3 DOWN providers. Those are different units — 183 entries across 30-ish providers. Conflating them would turn a three-lane problem into a fleet-wide scare, or the reverse.

Why --no-write: the probe writes the health state the router actually routes on. Running it normally would have replaced the live picture with a scan I had not yet explained — and this session has already shown what an unexplained state write costs. The refresh happens after the reasons above are established (filed as TR-247).

Filed as TR-247 with six criteria: a named root cause per lane with the response code and the request that produced it, crof's base_url corrected or explicitly disabled, kimi's 401 never presented as an outage, ollama-cloud's 11/11 diagnosed (retired probe id vs plan-blocked vs bad base_url), a reason string on any lane left disabled, and a sanctioned write run afterwards so the router's picture and the records agree.
