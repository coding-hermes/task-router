2. What broke, and what actually disarmed it

On 2026-09-25 the fleet locked up. The canonical census for 22:32–23:49: 447 proxied rows, 382 no-hops, 65 failed, 0 served — call density 6.1× normal. I caused it by pointing the live fleet at an unproven path; it was rolled back the same night (TR-169, P0).

The proximate trigger was unservable ratings: the classifier's requirement matrix asked for capability combinations no eligible lane could clear, so the resolver returned "no hops" and the request died blind. Two amplifiers were then found and fixed, both by measurement rather than reading:

DefectMechanismProof it is fixed
TR-182 — the breaker's blast radiusEvery failed hop was recorded with no failure class, defaulting to api_down — a HARD class that opens a provider-wide breaker for 1800s after three failures. Hop timeouts were recorded as provider outages, which is exactly the mechanism that turned a slow hop into a dead provider.Falsifier through the deployed path, 4/4: timed out→overload 120s · hop-wall-timeout→overload 120s · 429→quota_window 300s · connection refused→api_down 1800s (the legitimate case, preserved).
TR-184 — the fail-open boundaryThe row-writer raised AttributeError on a string payload and the helper whose job is filtering junk raised TypeError on an int. A resolver answering garbage could take down the ledger row that exists to describe it.Four payload shapes (string, None, int, mixed list) now produce a row; the invariant is pinned: no raise, and only objects survive — a dict in a mixed list is real evidence and is kept.
TR-184b — a shipped field's typeThe same work had changed skipped_hops from a count to a list. The ledger row shape is a contract: a consumer reading 0 breaks on [].The count stays a count; the detail is additive under skipped_hops_detail, and skipped_hops_source records whether the resolver or the derived exclusions produced the number.
Process failure worth stating plainly. I reported TR-158 as "pushed, guard running" and never read the result — the guard had failed. The type change had broken three test files, and I found them one 200-second guard run at a time. The fix for the process, not just the code: a guard verdict that has not been read is not a verdict, and a type change is a repo-wide edit — grep every consumer before committing. Both are now written into the fleet-ops skill.

4. Cost truth: real, unknown, or never fake

The pricing law in force: a plan-covered lane reports list price as public_price and the plan offset as normalized_price; a plan lane is never free; an unpriced lane is null with a reason; and a genuine promo zero stays zero. Three repairs landed against that law:

  • The import no longer copies the driver's 0.0. Subscription lanes' accounting reports zero; copying it verbatim left the rolling cost-per-task — the very input the sort feeds on — at zero fleet-wide. Live effect: hermes cost buckets with a real figure went 12 → 44, exactly-0.0 buckets went 95 → 0, and 27,727 rows moved off a bare $0 onto a plan-effective number with the ratio in the basis string.
  • Verify against a known ratio: 1M input tokens on gpt-6-luna prices at $0.00333362 — list $0.10 × that lane's own ÷30 plan ratio. A wrong offset cannot hide.
  • Backfill where a price arrived late: coverage 47 → 55 rows, and the skip census is the finding — 431 rows were served by lanes carrying no price at all, which token math cannot fix (they need a sticker).
Waiting on you (TR-179): 25 of xkiro's :free lanes carry no window cost; 22 have a knowable list sticker (e.g. minimax-m3:free → $0.010427). Pricing them satisfies the mirror rule — but it also moves the pinned chain heads (minimax-m3:free at 0.010427 loses to glm 0.005467 and luna 0.003867). That is a routing consequence, so it is your call, not mine.

6. Measured-cost ordering: why it is safe now

The feature at stake: order the chain by measured cost per completed task instead of sticker price. It was implemented, then reverted by the repo's own regression guard — router_spawn.py is symlinked into the live fleet, and a silent re-rank is not acceptable. What was missing was not courage but evidence, and measuring it produced the finding of the day:

# the same task, resolved under different sufficiency floors — the live store, 135 lanes / 289 stats rows
price                          head=xkiro/openai/gpt-6-luna
predicted_cost_per_task        head=xkiro/openai/gpt-6-luna      effective=price  coverage=0.0308  ranked=2/65  reason=below-coverage-floor
predicted_cost_per_task:3:0    head=xkiro/mistralai/mistral-large-2512  gate off
predicted_cost_per_task:1:0    head=ollama-cloud/glm-5.3-flash          ranked=4/65
predicted_cost_per_task:10:0   head=clinepass/glm-5.3                  ranked=1/65
The head is a function of the floor. Four floors, four different heads, each decided by 1–4 of 65 candidates while 61–64 lanes fell back to price. 169 of the store's 289 stats rows hold exactly one sample. A re-rank decided by two observations is not an improvement; it is a coin flip wearing a lab coat.

So a measurement must now be earned, twice over:

  • A sample floor (MEASURED_MIN_SAMPLES, default 3; per-call predicted_cost_per_task:5 or env ROUTER_SORT_MIN_SAMPLES; 0 restores the old behaviour). Below it a lane falls back to price and says why — below-floor is distinguishable from no-sample and from a measured zero, which is a real value.
  • A coverage bar (MEASURED_MIN_COVERAGE, default 0.5). Below it the whole ordering degrades to price and reports sufficiency{effective, reason, coverage, ranked, lanes} on the response — so "how much of this ordering rested on measurement" is always answerable.

Proven after landing: DEFAULT_SORT is still price, the default resolve head is unchanged, and the default response carries no sufficiency claim. Nothing about the live fleet's ordering moved. What changed is that the flip is now safe to offer whenever you want it: it cannot silently swap a head, and it will turn itself on as real coverage accumulates.

Two different diseases. mechanical is asked for in 55 rows but only 16 lanes carry any tier for it — its evidence comes from a small PROFILE_TAGS estimate mapping, so it is thin, not unknown. guard, review and spec_docs are the opposite: well-populated categories where only 4–10 eligible lanes clear the level being asked. The first needs more evidence; the second needs a less demanding requirement. Both change routing, so both are yours.

A correction to my own record. I had written that "no evidence exists anywhere in the repo" for mechanical. That was wrong — evidence exists for 16 lanes and is thin. The distinction matters, because the two diagnoses have different fixes and the wrong one sends the next session hunting for a source that already exists.
